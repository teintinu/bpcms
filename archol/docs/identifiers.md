# Identifiers, references and the application lock

Archol gives every named declaration a **stable id**. References are typed
nodes that point to those ids instead of embedding a copy of the target. This
keeps the AST small, acyclic and usable by builders that generate other
languages.

## The lock file: `<app>.lock`

One lock per application, in the **same directory and with the same basename**
as the application file, changing only the extension:

```text
examples/applications/example.com/app/loja-do-joao/
  loja-do-joao-application.archol
  loja-do-joao-application.lock      ← generated lock
```

The lock is a plain **CSV with two columns, `id,path`**, one identifier per
line (no header, no commas inside a path). It is generated by
`archol lock --app <application>` (or **Archol: Update Identifier Lock**) and
versioned with the source.

- **Delete the file to reset the ids.** New locks start again at `a`.
- **Automatic refresh:** selecting the application writes the lock immediately;
  while editing `.archol` files the plugin refreshes it after a **10 s
  debounce** (`archol.lockDebounceMs`), only when a changed file belongs to the
  current application closure.
- **Ids are assigned at the end of compilation, only for used paths.**
  Unused declarations get no id and no line.
- **Pinned entries come first**, then generated entries in id order.
- Duplicate ids caused by concurrent branches are a merge responsibility; the
  loader rejects duplicates and tells you to fix the merge.

```csv
checkoutStatus,example.com/services/checkout#shape/CheckoutStatus*
a,example.com/services/billing#service
b,example.com/services/billing#shape/InvoiceStatus/value/Overdue
c,example.com/services/billing#document/Invoice/field/status
```

### Used identifiers

During compilation references are resolved to **paths**, not numbers. At the
end:

- every artifact in the application closure is a root and gets an id;
- pending comments (`TODO`, `REVIEW`, ...) are metadata and never get ids or
  lock lines;
- a field, enum value, or parameter gets an id only when something references
  it (`invoice.status`, `== Overdue`, type references, roles, ...);
- identifiers never referenced stay without an id and without a lock line;
- pinned entries are kept even if unused.

### Id rules

Generated ids are **sequential lowercase base-36 strings starting at `a`**.
The first character is **always a letter** (an identifier cannot start with a
digit); later characters may be letters or digits:

`a`, `b`, …, `z`, `aa`, `ab`, …, `az`, `a0`, …, `a9`, `ba`, …, `z9`, `aaa`, …

New ids are allocated in **descending reference count**; ties are broken by
path. Identifiers that are only roots (never referenced) get the remaining ids
after all referenced ones. Existing ids are never changed; only new paths
consume new numbers. They never duplicate: the allocator skips ids already
present (including pinned/custom ones). They are valid identifiers in most
target languages.

### Pinned ids with `*`

After the compiler writes an id, you may **edit the lock line** and append `*`
to the end of the path's identifier name:

```csv
checkoutStatus,example.com/services/checkout#shape/CheckoutStatus*
```

Pinned entries are:

- always written **at the top** of the file, in their original order;
- never renumbered or pruned, even if the declaration disappears;
- skipped by the generator, so no duplicate is created;
- cleaned of the `*` only for matching the declaration path (the marker stays
  in the file).

The compiler's job with `*` is only to preserve it across lock rewrites and
keep those lines first.

### Safe paths

`path` locates the identifier without exposing a filesystem path:

| Identifier | Path |
| :--- | :--- |
| Application | `<app-uri>#application` |
| Service | `<service-uri>#service` |
| Artifact | `<service-uri>#<kind>/<Name>` (`document`, `shape`, `view`, `process`, ...) |
| Document field | `<service-uri>#document/<Document>/field/<field>` |
| Enum value | `<service-uri>#shape/<Shape>/value/<Value>` |
| Process parameter | `<service-uri>#process/<Process>/param/<param>` |

## AST annotations

Declarations carry `id`; references carry `ref` (`refKind` names the target
kind). Optional fields are omitted when absent.

```json
{
  "kind": "Binary",
  "op": "==",
  "left": {
    "kind": "MemberAccess",
    "name": "status",
    "fieldRef": "c",
    "object": { "kind": "Identifier", "name": "invoice" }
  },
  "right": {
    "kind": "Reference",
    "refKind": "enumValue",
    "name": "Overdue",
    "ref": "b"
  }
}
```

| Field | Meaning |
| :--- | :--- |
| `id` | declaration id from the application lock |
| `ref` | target declaration id (references) |
| `refKind` | target kind (`enumValue`, `document`, `role`, ...) |
| `fieldRef` | id of the document field addressed by a member access |
| `typeRefId` | id of the type named by a type reference |

From that `if`, a builder can walk `Overdue` → enum value id → shape
`InvoiceStatus` → service `example.com/services/billing`, and back through
`invoice.status` → field `status`.

## Reference index

Usage lists live in the semantic index (`archol/usages` in the LSP), not inside
the AST. For every id:

- declaration location (`archol/declaration`);
- every usage: file, span and kind (`enumValue`, `fieldRef`, `artifactRef`,
  `roleRef`, `typeRef`, ...).

The AST explorer exposes **Go to Declaration** and **Find Usages** for these
ids.

## Application closure

Compilation starts from an application. `archol check`, `archol lock`,
`archol links` and the LSP require an application and only load its closure:
entry-point services plus services reachable through `imports`.

Service aliases and imports are references too: an application `services { "<uri>" as Alias }`
entry and a service `imports { service "<uri>" as Alias }` entry carry the `ref` of the
service declaration, so the explorer can jump from `Identity` to the service file.

Files outside the closure are inert. The LSP treats them as **commented out**:
no hover, completion, definition, references or symbols, a single information
diagnostic, and `archol/ast` returns `commentedOut: true`.

The VS Code setting `archol.application` selects the current application; the
status bar shows it and **Archol: Select Application** changes it.
